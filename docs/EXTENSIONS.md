# Extensions: the runtime (0.17.0)

Krunk runs its own subset of Chrome's Manifest V3 (the engine, CEF, has no extension system
that Krunk uses). This document describes the runtime as of 0.17.0: why MetaMask installed
but did not load before, what was built, how the pieces talk, and what is still not there.
Nothing here is specific to one extension: the fixes are the general ones a wallet-class
extension needs.

Code: `core/src/ext.rs` (manifest, packages, the content bundle), `core/src/ext_runtime.rs`
(the parts that need no browser: worker bootstrap, addresses, ports, messages, registered
scripts, errors), `app/src/browser/ext.rs` and `app/src/browser/ext/runtime.rs` (the host),
`ui/inject/ext-page.js` (the `chrome.*` shim of pages and of the background worker),
`ui/inject/ext-worker.js` (the worker's bootstrap), `ui/inject/ext-content.js` (the shim of
content-script worlds).

## Why MetaMask "installed but did not load" (0.16.0)

Observed on Windows with MetaMask 13.56.0 (see `.pipeline/evidence-0.17.0/diagnosis.md`), in
the order the causes stop it:

1. **The background was not a worker.** Krunk ran the service worker's file as a classic
   script in a hidden page. `self.serviceWorker` did not exist, so
   `"activated" === self.serviceWorker.state` threw and the start-up chain never ran; no
   `install` event either. `importScripts` was an `eval` of a file fetched with XHR, which the
   extension pages' CSP (`script-src 'self' 'wasm-unsafe-eval'`) forbids, so the webpack
   chunks could never have loaded. `chrome` was a property of that page's `window`.
2. **No ports.** `chrome.runtime.connect` threw "not provided". The popup, the full-page UI and
   the content script all talk to the background through ports: the popup showed a spinner
   for ever.
3. **`world: "MAIN"` content scripts were dropped.** `scripts/inpage.js` is what defines
   `window.ethereum`.
4. **The origin.** Extension pages are served from `https://<id>.ext.krunk.invalid`; MetaMask
   decides whether a port comes from its own UI by
   `new URL(port.sender.url).origin === "chrome-extension://" + chrome.runtime.id`.
5. APIs on the way to a working wallet that were stubs or missing: popup-type windows (the
   connect and signature prompts), `offscreen`, `scripting.registerContentScripts`,
   `unlimitedStorage`, `management.getSelf`, `runtime.getContexts`.
6. `console.error` of extension contexts went nowhere, so the next failure could not be seen.

## The background is a worker

```
host (Rust)  <── page bridge ──>  hidden page /_krunk/background.html   (relay only)
                                        │  new Worker("/<dir>/__krunk_sw__.js")
                                        ▼
                                  dedicated Worker
                                    1. bridge: takes postMessage / addEventListener
                                    2. ext-page.js: chrome.*, self.serviceWorker, …
                                    3. importScripts("./<service worker>")   (or import())
                                    4. install + activate (fresh installation only), "bgReady"
```

* The hidden page gets `ext-page.js` like every extension page. On
  `/_krunk/background.html` the shim does one thing: it reads `/_krunk/background.json`
  (`{ boot, module, install }`, generated by the host), starts a dedicated `Worker` on `boot`
  and relays: `worker → {__krunk: m} → host` and `host → {__krunkIn: m} → worker`. The page
  itself has no `chrome`.
* The worker's script is `ui/inject/ext-worker.js` with the shim and the service worker's
  file name filled in (`core::ext_runtime::worker_bootstrap`). The host serves it **next to
  the service worker's own file** (`__krunk_sw__.js` in the same folder), so relative
  `importScripts`, static and dynamic imports and bundlers' automatic public paths resolve as
  in Chrome. `importScripts` is the engine's own; nothing is evaluated from text.
* The bootstrap takes `postMessage` and `addEventListener` first and the shim takes every
  global it needs later (`XMLHttpRequest`, `setTimeout`, `crypto`, `navigator`, `Event`,
  `dispatchEvent`) before the extension runs: SES / LavaMoat remove or freeze globals. The
  extension's own `message` listeners never see the host's messages.
* The shim gives the worker `chrome` and `browser` as globals, `self.serviceWorker`
  (`state: "activated"`), `self.registration`, `self.clients`, `self.skipWaiting()`. There is
  no installing or waiting phase. `install` and `activate` are dispatched (with `waitUntil`)
  on the first start after an installation or update only, like Chrome does it; an ordinary
  start has none.
* Events the host has for the background (`onInstalled`, `onStartup`, messages, connections,
  alarms) are queued until the worker posts `bgReady`, which the bootstrap does when the
  service worker's script has run (or failed: the error is reported and `bgReady` still
  comes). A worker that says nothing for a minute gets an error in the list and its events.
* `"type": "module"` service workers: a module `Worker`, the script loaded with `import()`.
* The worker is never stopped while the extension is enabled (Chrome stops idle service
  workers; extensions written for that are fine with one that stays).

## Addresses: Krunk's origin, Chrome's names for senders

One mapping, applied at the boundaries (`core::ext_runtime::chrome_url` / `krunk_url`):

| What | Form | Why |
|---|---|---|
| Where pages and files are served, `location`, `runtime.getURL()`, `tabs.Tab.url`, `runtime.getContexts().documentUrl` | `https://<id>.ext.krunk.invalid/…` | it must load: `fetch`, `<iframe src>`, `new Worker`, `tabs.create` use it as is |
| `sender.url`, `sender.origin` of an extension page or the background (messages and ports) | `chrome-extension://<id>/…` | extensions compare it with the origin they build from `runtime.id` |
| `runtime.id` | `<id>` | |
| An address an extension builds itself (`chrome-extension://<id>/page.html`) and passes to `tabs.create`, `tabs.update`, `windows.create`, `offscreen.createDocument` | mapped to Krunk's form | |

Content-script senders are web pages: their `url` and `origin` are the page's, with `tab` and
`frameId` (0 for the top frame).

**To be checked on Windows:** `new URL("chrome-extension://<id>/x").origin` must be
`"chrome-extension://<id>"` in Krunk's engine (it is in Chrome and in a CEF built with the
extensions module; in a headless test Chromium it is `"null"`). The fixture's self-test has
a line for it. If it is `"null"`, the scheme has to be registered as a standard scheme in
the engine (`OnRegisterCustomSchemes`) — nothing in the shims can change what `URL` computes.

Not done: the `Origin` header of an extension page's network requests is Krunk's
(`https://<id>.ext.krunk.invalid`), and cross-origin requests follow CORS; Chrome sends
`chrome-extension://<id>` and exempts the manifest's `host_permissions` from CORS. A server
that allows a wallet's extension origin by name will refuse these requests.

## Ports and messages

The host knows each of an extension's contexts as an **end**: the background, the action
popup, the offscreen document, one of its windows, a page in a tab, a content-script world of
a frame. Which end a request comes from is decided by the view it arrives through (or the
DevTools binding of the content world), never by the message.

* **Ports** (`runtime.connect`, `runtime.onConnect`, `tabs.connect`, `Port.name`, `.sender`,
  `.postMessage`, `.onMessage`, `.onDisconnect`, `.disconnect`). The opener chooses an id and
  tells the host (`port.open`); the host offers the port to the receivers
  (`runtime.connect`: every other page context of the extension; `tabs.connect`: the
  extension's content worlds in that tab, one frame with `frameId`) with the sender it
  computed. A receiver without `onConnect` listeners closes its end at once, one with
  listeners accepts. The table (`core::ext_runtime::PortTable`) routes messages (opener → all
  receivers, receiver → opener) and closes: when the last receiver is gone the opener gets
  `onDisconnect`, with `runtime.lastError` "Could not establish connection. Receiving end does
  not exist." if nobody ever accepted. A port only carries messages between ends that are on
  it; an extension cannot name another extension's port (the table is keyed by extension).
* **Context loss** closes ports from that side: a tab closed, a frame navigated (its world is
  destroyed), an extension page reloaded or navigated away, the popup closed, a window
  closed, the offscreen document closed, the background stopped, the extension disabled or
  removed.
* **Messages.** `runtime.sendMessage` goes to every other page context of the extension, so
  pages in tabs, windows and the offscreen document now get `onMessage` (and
  `storage.onChanged`). A context without listeners answers "none", one whose listeners do
  not answer "empty", and the first real answer wins (`core::ext_runtime::Broadcast`):
  `undefined` when somebody listened, Chrome's error when nobody did. A listener may return
  `true`, a promise, or call `sendResponse`.
* `onConnectExternal` / `onMessageExternal` never fire: there is no messaging between
  extensions or from web pages (`externally_connectable`).

## Content scripts

* **Isolated world** (one per extension, as before): `chrome` and `browser` are now globals
  of the world as well as arguments. The files of one `content_scripts` entry are one function
  body, so what the first file declares (`const`, `class`, functions) the next ones see; the
  bundle is no longer forced into strict mode. A file that starts with `"use strict"` gets a
  function of its own.
  Difference to Chrome: declarations are shared within an entry, not between entries, and an
  exception in one file skips the rest of its entry.
* **`world: "MAIN"`**: a second bundle (`core::ext_runtime::main_bundle`) installed without
  a world name, so it runs in the page's own world at document creation, before the page's
  scripts for `document_start`. No extension API there, as in Chrome. Same match rules,
  `all_frames`, `run_at`; never on Krunk's own pages; private tabs only when allowed.
* **`scripting.registerContentScripts` / `getRegisteredContentScripts` /
  `unregisterContentScripts`**: kept in memory until Krunk closes (extensions register again
  at start), ids must be unique, files must be inside the package. Registered scripts are
  bundled like the manifest's; a change reinstalls the bundles in open tabs.
  `updateContentScripts` is not provided.
* **`scripting.executeScript`** answers with the real result (by value; a promise is
  awaited), for `files` and for `func` + `args`, in the extension's world or with
  `world: "MAIN"` in the page's. One result (the top frame); `allFrames` / `frameIds` are not
  provided.

## Pages

* **Offscreen document** (`offscreen.createDocument` / `closeDocument` / `hasDocument`): one
  hidden page per extension, with the full API and messaging. Reasons are not checked.
* **Windows.** `windows.create({ type: "popup" | "panel", url: <a page of the extension> })`
  opens a small Krunk window with a normal title bar showing that page (`width`, `height`,
  `left`, `top` in DIP, kept on the screen). `windows.get` / `getAll` / `getCurrent` /
  `update` (`focused`, position, size) / `remove`, `onRemoved`, `onFocusChanged`;
  `window.close()` in the page closes it. Browser windows report `left`, `top`, `width`,
  `height` too. Any other `windows.create` opens a tab. At most 8 per extension.
* **Sandboxed pages** (manifest `sandbox.pages`): served with the manifest's
  `content_security_policy.sandbox` (or Chrome's default), always starting with `sandbox`, so
  they have a unique origin; they get no extension API (the host refuses their requests).
  Which page is sandboxed is decided on the path as the file is found (percent-decoded,
  without regard to case, by the file system's own name for an existing file), the same form
  every comparison with a manifest list uses (`core::ext_guard::package_path`).
* `storage.session` (memory), `storage.local` up to 256 MiB instead of 10 MiB with the
  `unlimitedStorage` permission (requests up to 64 MiB); a `set` over the limit is refused
  whole with "QUOTA_BYTES quota exceeded", and the file is replaced by a rename of a synced
  temporary file. `management.getSelf`,
  `permissions.getAll/contains/request`, `i18n.getAcceptLanguages`, `runtime.getContexts`.

## Stand-ins and absences

| API | Behaviour |
|---|---|
| `notifications` | calls resolve (`create` with the id); nothing is shown |
| `cookies` | `getAll` → `[]`, `get` → `null`; nothing is set |
| `webRequest` | listeners are accepted and never called |
| `runtime.onUpdateAvailable`, `onSuspend`, `tabs.onCreated`, … | accepted, never fire |
| `sidePanel`, `identity`, `debugger`, `nativeMessaging`, `history`, `bookmarks`, `downloads`, … | absent (`undefined`) |
| `management` | `getSelf` only |
| `declarativeNetRequest` dynamic / session rules, `scripting.updateContentScripts` | reject |
| `externally_connectable`, messaging between extensions | not provided |
| service worker `fetch` events, Cache-based offline start, push | not provided (the background is a dedicated worker) |

Every stand-in and absence an extension touches is listed once under **Not in Krunk** on its
card on `krunk://extensions`.

## Errors

`console.error`, uncaught errors and unhandled promise rejections of every context of an
extension (background worker, popup, pages in tabs, offscreen document, windows, content
scripts) go to `krunk.log` as `extension <name>: <message> [<context>, <file>:<line>]` and to
the extension's **Errors** list on its card on `krunk://extensions` (Details): newest first,
with the context and file:line, repeats counted, at most 50, in memory until Krunk closes.
The shims report them (they wrap `console.error` and listen for `error` and
`unhandledrejection` in their context); uncaught errors of content-script worlds come from the
engine (`Runtime.exceptionThrown`, the extensions' worlds only). Page console output of web
pages is still not logged.

Text an extension supplies reaches krunk.log capped and on one line (control characters
become spaces: no forged log lines), and at most 120 lines per extension, kind (errors,
content-script calls) and minute; the Errors list is not affected, and `KRUNK_EXT_LOG=1`
lifts the limit.

## Security

Unchanged: extension pages and the worker run under `script-src 'self' 'wasm-unsafe-eval'`
(no `unsafe-eval`, no inline scripts); every request is attributed by the view or binding it
arrives through and checked against that origin's extension id; an extension reaches only
its own storage, messages, ports, windows and offscreen document; content worlds exist only
where the extension may run and never on Krunk's own pages; `scripting.*` needs the
`scripting` permission and a tab that has the extension's world. New in 0.17.0:

* MAIN-world scripts run in the page's world like any page script: they get no binding and no
  API, and the page can see what they define (as in Chrome).
* A content world reports whether it is the top frame and its address for `sender`; the host
  accepts the address (the top frame's too) only on the origin the engine reported for that
  world, and `sender.origin` is that origin (`core::ext_guard::content_sender`). The tab's
  address is not used: it already names the next page while a navigation is pending. The
  information only ever reaches the same extension.
* An address an extension gives to `tabs.create`, `tabs.update` or `windows.create` is not
  the host's: its own pages and `http(s)` only, no local file, none of Krunk's pages, no other
  extension's page (`core::ext_guard::may_open`). Without an address it is a new tab.
* No content scripts, MAIN-world scripts or `scripting.*` on `file:` documents (Chrome's
  default without "Allow access to file URLs"; a `file://*/*` pattern is accepted and unused).
* `scripting.executeScript` / `insertCSS` need host access to the document: a host pattern in
  `host_permissions` / `permissions` that covers the origin the engine reports for the world
  the script runs in (content script `matches` grant nothing), or `activeTab` after the user
  clicked the extension's button, for that tab while it stays on that origin. `world: "MAIN"`
  needs the top frame's world.
* **`web_accessible_resources`** is enforced (`core::ext_guard::WebAccess`, `request_allowed`)
  by the tabs' network policy, which knows the origin that asks (the engine's request
  initiator). The extension's own documents, the host's own navigations (address bar, tabs the
  host or the extension opened, history) and Krunk's pages load any file. A web page — by a
  sub-resource, a frame, `fetch`, a link, `location` or `window.open` — gets only what a
  Manifest V3 entry lists for its origin (`matches`), plus the style sheets of content scripts
  (the shim links them into the page). Another extension gets nothing. A server's redirect
  leads to an extension page only when it is listed, and a link the host opens in a new tab
  for a page (Ctrl or middle click, "Open in new tab") is checked against the document the
  opener shows. `Access-Control-Allow-Origin: *` is sent
  with listed files only. The action popup, offscreen documents, the extension's windows and
  the background worker are not tabs and are not affected.
  A content script's `fetch()` of a file of its own extension (GET, up to 8 MiB) is answered
  by the host through the world's binding, listed or not, as Chrome allows it; the page's own
  `fetch` cannot use that. `XMLHttpRequest` and elements a content script adds to the page
  (`<img>`, `<script>`, `<iframe>`) are the page's requests and need a listed resource, as in
  Chrome. Remaining gap: a sandboxed page of the extension has an opaque origin, so in a tab
  whose address is the extension's a request from an opaque origin is let through when the
  manifest has sandboxed pages.
* `storage.session` is for the extension's pages and background (Chrome's `TRUSTED_CONTEXTS`):
  a content script's calls are refused ("Access to storage is not allowed from this context.")
  and it hears no changes of that area, until a page or the background calls
  `storage.session.setAccessLevel({ accessLevel: "TRUSTED_AND_UNTRUSTED_CONTEXTS" })`
  (kept in memory, per extension and area, until the extension restarts; `local` and `sync`
  can be closed the same way).
* Sandboxed pages are the one place with `unsafe-eval`: unique origin, no API.
* Ports per extension are capped (2048), registered scripts (100), windows (8), errors (50).
