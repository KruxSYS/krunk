# Krunk account sync: plan (design; implementation needs operator approval)

Status: proposal, 2026-11-05. Nothing in this document is implemented yet.
Companion documents:
- `PROTOCOL.md`: the exact cryptography, flows, record format and API;
- `THREAT_MODEL.md`: attackers, guarantees and residual risks;
- `OPEN_QUESTIONS.md`: decisions and inputs only the operator can provide.

The requirements checklist (brief items 1–13 → sections) is in §10.

---

## 1. Summary
Optional Krunk accounts let a user sync these between their Krunk browsers:
- history, bookmarks, passwords, settings and open tabs;
- new-tab pins, the ad-block allowlist and the never-save list.

The user registers on https://krunk.209.wf and links each browser with a short code. Everything
is **end-to-end encrypted** on the device. The server stores ciphertext and authenticated key
directories, and can't read the data. A database leak or a compromised website can't read it
either.

Keys come from one of three sources:
- a **sync passphrase**, generated by default (6 words);
- a printable **recovery key**;
- **approval from a linked device**, confirmed with a 6-digit code that the user types into the
  new device.

If the passphrase, the recovery key and every device are all lost, the data is unrecoverable.
The UI says so plainly.

## 2. Opt-in and offline-first (requirement 1)
- **Sync is off by default.** Krunk stays fully usable without an account; every existing
  feature works unchanged.
- **No sync request is made until linking.** The `api/v1` endpoints are contacted only after the
  user clicks *Link Krunk account* in `krunk://settings` → Sync. Before that:
  - no sync state file exists;
  - no timer runs;
  - no DNS lookup for the sync API is made beyond the website and updates Krunk already uses.

  A test checks this: a fresh profile run for 10 minutes behind the logging proxy shows no
  `/api/` request (the S6 acceptance test).
- **Unlinking** (`krunk://sync` → *Unlink this device*):
  - calls `POST /api/v1/device/unlink`, which revokes the device and starts key rotation for
    the others;
  - deletes `sync.json` and the sync tables' state;
  - stops all timers.

  The user chooses **Keep local data** (the default: history, bookmarks and passwords stay as
  normal local data) or **Delete synced data from this device**. Deleting removes the items that
  came from sync, using `sync_items` provenance, and keeps items created locally.
- **Offline:** every change is written locally first and queued (`sync_queue`). Sync catches up
  when the network returns. Sync errors never block browsing, saving bookmarks or the vault.

### 3.2 Decisions, with the alternatives considered
| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| D1 | Rust (axum 0.8) API with PostgreSQL 18 | Go or Node services; SQLite on a volume | It shares the Rust types and crypto test code with the client, is memory-safe and uses the toolchain we already have. Postgres gives transactional CAS, concurrent writers and standard `pg_dump` backups. SQLite would be simpler, but the brief asks for Postgres and we may run several API workers. |
| D2 | Account pages are static HTML/JS served by Caddy, calling a JSON API | Server-rendered templates (askama) | Both work under `script-src 'self'`. Static pages keep one API surface (used by the website and, partly, by clients), carry no template-injection risk, and reuse Caddy's caching and headers. The cost is that JS is required; Turnstile requires it anyway. |
| D3 | The **account password** and the **sync passphrase** are separate secrets | One password split into an auth half and a key half on the client (as Firefox Accounts "onepw" does) | The account password is typed into the *website*. Unifying the two would put key material into website JS, which a compromised site could steal (THREAT_MODEL 4). Keeping them separate keeps the website out of the key path. The UX cost is a second secret, which is generated and saveable. |
| D4 | Asymmetric wrapping (HPKE, RFC 9180, via the `hpke` 0.15.1 crate: seals to device and escrow keys), plus a symmetric **recovery root RR** under the passphrase and recovery key; the escrow keypair is derived from RR | Baseline: AK wrapped symmetrically under the passphrase and recovery key | With asymmetric wrapping a remaining device can rotate keys after a revocation without anyone re-entering a secret. The RR escrow and the authenticated directories stop a malicious server from planting keys, which a naive "seal to the passphrase public key" design would allow (review findings 1, 2, 7). |
| D5 | A separate **PAK** for passwords, held only inside the vault | Passwords under AK | AK sits on disk under DPAPI. If passwords used it, synced passwords would be weaker than the local vault (THREAT_MODEL G4). |
| D6 | JSON envelopes, XChaCha20-Poly1305 with random 24-byte nonces, padding buckets | CBOR or protobuf; AES-256-GCM | JSON is trivial in Kotlin and in serde. XChaCha's 192-bit nonces make random nonces safe at any volume, and we already use the crate. AES-GCM's 96-bit nonces would need counters. |
| D7 | Server `seq` per account, plus HLC versions and a merge rule per collection | Vector clocks; CRDT libraries (automerge) | The small set of collections has well-understood merges: union for history, LWW for the rest, and a tree repair for bookmarks. A CRDT would add a large dependency and on-disk format that Android would also have to carry. |
| D8 | Opaque random tokens, with only HMAC hashes stored | JWT access tokens | Revocation takes effect at once and there is no signing-key exposure. The DB lookup per request costs nothing at this scale. |
| D9 | A device grant on the RFC 8628 pattern | OAuth authorization code + PKCE with a loopback redirect | No local HTTP listener is needed, it works the same on Android, and the user approves on the website they already trust. Its phishing risk is mitigated (PROTOCOL §6.1), and a link alone grants no keys. |
| D10 | Cloudflare Turnstile | hCaptcha; a self-hosted proof-of-work challenge | Cloudflare is already in front, it is privacy-friendly and requires no user interaction in most cases, and the brief asks for it. |
| D11 | An external SMTP provider | Our own MTA container | Deliverability (SPF, DKIM, reputation), and outbound port 25 is often blocked. An outbox table makes sending asynchronous and retryable. |
| D12 | `api` runtime on distroless `cc-debian13:nonroot` | `debian:trixie-slim` | A minimal attack surface (no shell, no package manager). The health check is the binary's own `healthcheck` subcommand. |
| D13 | Eager rekey after a revocation | Lazy rekey (re-encrypt only when a record is next written) | Eager rekey enables `min_record_epoch`, which rejects old-epoch injection, and lets the old keys be dropped quickly. Data volumes are small (quota §6). |
| D14 | A generated 6-word passphrase by default | A user-chosen passphrase with a strength meter | The passphrase protects `rr_wrap_pp` against offline guessing after a DB leak. 77 bits under Argon2id 128 MiB is safe. Custom passphrases are allowed only past a strict gate (PROTOCOL §5.1). |
| D15 | A shared `core::sync` in Rust, used on Android via UniFFI | Reimplementing it in Kotlin with Tink and Bouncy Castle | One implementation of subtle crypto and merge code, and the Argon2id memory footprint stays native. The test vectors cover both paths in case Android must diverge. |

### 4.2 Accounts (requirement 2)
- **Email and password.**
  - Email: case-insensitive, unique, at most 254 characters, syntax-checked. It must be verified
    before linking: a link approval is refused until it is.
  - Password policy: 10 to 256 characters (Unicode NFKC), not equal to the email, and not in a
    bundled top-100k common-password list. An HIBP k-anonymity check is optional
    (OPEN_QUESTIONS).
- **Hashing:**
  `Argon2id(input = HMAC-SHA256(PASSWORD_PEPPER, nfkc(password)), salt = 16 random bytes, m = 65536 KiB, t = 3, p = 1, out = 32 bytes)`,
  stored as a PHC string together with a `pepper_id` so the pepper can rotate. Crates: `argon2`
  0.6 and `hmac` 0.13.
  - A semaphore allows 4 concurrent hashes, so peak memory is 256 MiB (the container memory
    limit is 768 MiB).
  - An unknown email still runs one hash against a dummy PHC, so login timing doesn't reveal
    whether an account exists.
- **Email verification:** a random 32-byte token in a link (`/account/verify?token=…`), valid
  24 h and single-use. Only its HMAC hash is stored. `resend-verification` needs Turnstile and is
  rate-limited.
- **Password reset:**
  - It works like verification, but the token lasts 1 h.
  - It sets the new password, revokes **all web sessions** and sends an email.
  - It **does not touch devices, keys or synced data**. The server has no keys, so the data
    survives a reset (THREAT_MODEL G6). Linked devices keep syncing.
- **2FA:**
  - **TOTP** (RFC 6238, SHA-1, 6 digits, 30 s, ±1 step, `totp-rs` 6), optional. The secret is
    encrypted at rest with XChaCha20-Poly1305 under `TOTP_ENC_KEY` from `.env`. There are 10
    single-use backup codes, Argon2id-hashed with the same parameters as passwords.
  - **WebAuthn / passkeys** come later (S11+, `webauthn-rs` 0.6) as a second factor or a
    passwordless web login. They are never used for sync keys.
- **Generic errors:** login, register, reset and resend give the same response whether or not
  the account exists. Register always answers "check your email". For an existing address, that
  email says "someone tried to register with your address".
- **Rate limits:**
  - **Per IP:** in memory, `governor` 0.10, keyed by the *trusted* client IP (§4.4).
  - **Per account:** stored in `accounts.failed_logins` and `locked_until`, with exponential
    back-off after 5 failures (1, 2, 4 … 60 min).

  The numbers are in PROTOCOL §11.

### 4.3 Tokens, sessions and devices (requirements 3, 6, 7, 8)
- **Device tokens:**
  - **Access tokens:** opaque, 32 random bytes, valid 15 minutes.
  - **Refresh tokens:** opaque, 32 random bytes, rotated on every use and grouped in a
    *family* per device. They expire after 90 days without use; there is no absolute limit
    while in use.
  - **Reuse detection:** presenting an already-rotated refresh token revokes the family, unlinks
    the device, starts rotation (PROTOCOL §7) and emails the user.
  - **Storage:** the server keeps only `HMAC-SHA256(TOKEN_HMAC_KEY, token)`. The client keeps
    the refresh token in `sync.json` (DPAPI on Windows, Keystore on Android) and the access
    token in memory only.
- **Web sessions:**
  - **Cookie:** `__Host-krunk_session=<32 random bytes, b64url>` with `Secure`, `HttpOnly`,
    `SameSite=Strict` and `Path=/`, and no `Domain` (required by the `__Host-` prefix).
  - **Lifetime:** 12 h idle, 7 days absolute.
  - **CSRF:**
    - a per-session CSRF token, returned at login and sent as `X-Krunk-CSRF` on every
      state-changing request;
    - a strict `Origin`/`Sec-Fetch-Site` check (`same-origin` only);
    - `SameSite=Strict` on top.
  - **Re-authentication:** sensitive actions need a successful `web/reauth` (password, plus
    TOTP if enabled) within the last 10 minutes (`reauth_at`). They are: approving a link,
    revoking a device, revoke-all, export, sync reset and account deletion. Revoking a single
    web session needs no re-auth, so a suspicious session can be killed quickly.
- **Session tracking (requirement 7):**
  - Every web session and every device session records `created_at`, `last_used_at`,
    `user_agent` (truncated to 256 characters), the IP and the country (Cloudflare's
    `CF-IPCountry`).
  - The account page (`/account/sessions`) and `krunk://sync` list them with the IP masked
    (/24 or /48). The user can revoke one or all.
  - **IP retention: 90 days**, counted from when the IP was recorded. A daily job:
    - sets `web_sessions.ip = NULL` where `last_used_at` is more than 90 days ago;
    - sets `devices.last_ip = NULL` where `last_sync_at` is more than 90 days ago;
    - deletes `ip_events` older than 90 days.

    Link grants, which also carry an IP, are deleted within about an hour anyway. The country
    is kept while the session or device exists. Configurable as `IP_RETENTION_DAYS`
    (OPEN_QUESTIONS Q6).
- **Devices (requirement 6):**
  - **What the server holds:** `id` (UUIDv4, minted at link approval); `short` (u16); `platform`;
    `label` (a non-secret string from the client, such as "Krunk 0.3 on Windows 11");
    `created_at`; `last_sync_at`; `last_country`; `revoked_at`.
  - **Public keys** live in `ak_dir`/`pak_dir`, written by clients.
  - **Device name:** user-chosen and **encrypted**, as a `device_meta` record. Only Krunk shows
    and edits it; the website shows "Device 3 · Windows · last sync 2 h ago".
  - **Rename versus revoke:** the account page lists and **revokes** devices. **Renaming** is done in
    Krunk (`krunk://sync`), because names are end-to-end encrypted and the website must never
    hold the key to write them. This deliberately narrows the brief's "rename on the account
    page".
  - **Revoking** from the website or from a device kills its tokens at once and starts
    rotation, carried out by a remaining device (PROTOCOL §7).
- **Email notifications** (via the outbox; templates in S2):
  - a new device linked;
  - a password changed or reset;
  - 2FA enabled or disabled;
  - refresh-token reuse;
  - escrow fetched (a new device is restoring);
  - a device revoked;
  - an approval requested;
  - the account deleted (a receipt).

### 4.4 Client IP and Cloudflare (requirement 8)
- **Caddy decides the client IP.**
  - `servers { trusted_proxies static <Cloudflare ranges + the configured internal hop> }` and
    `client_ip_headers CF-Connecting-IP`.
  - The Cloudflare ranges come from https://www.cloudflare.com/ips-v4 and /ips-v6. They are
    pinned into a generated `cloudflare-ips.caddy` file, refreshed by a script during release,
    and the date is recorded.
- **How `api` learns it:** Caddy sends `X-Krunk-Client-IP: {client_ip}` (overwriting any value
  from the client) together with `CF-IPCountry`. `api` honours those headers **only** when the
  TCP peer is the `web` container on the compose network, and otherwise uses the peer address.
  No other forwarding header is trusted.
- **Open question Q8:** how live traffic reaches Caddy (directly from Cloudflare, through a
  tunnel, or through the ai-pipe proxy) decides which address goes into `trusted_proxies`. If
  the hop is an ai-pipe proxy, that proxy must pass `CF-Connecting-IP` through unchanged, and
  only that proxy is trusted.
- **TLS:** it terminates at Cloudflare; the Cloudflare → origin leg is per the operator's
  setup. Clients use normal WebPKI validation with **no pinning**. Pinning would break whenever
  Cloudflare rotates certificates, and the E2E encryption already protects the data. A
  compromised TLS path yields only metadata and ciphertext.
- **Caching:** `Cache-Control: no-store` on every `/api/*` and `/account/*` response, set by both
  Caddy and `api`. Cloudflare doesn't cache JSON by default, and `no-store` prevents any
  configuration mistake.

### 4.5 Cloudflare Turnstile (requirement 2)
Docs:
- server-side validation: https://developers.cloudflare.com/turnstile/get-started/server-side-validation/
- CSP: https://developers.cloudflare.com/turnstile/reference/content-security-policy/
- testing: https://developers.cloudflare.com/turnstile/troubleshooting/testing/

- **Where:** the widget appears on the **register, login, password-reset request and
  resend-verification** forms (plus account deletion). Each form has its own `action`:
  `register`, `login`, `reset`, `resend` or `delete`. It is loaded with
  `<script src="https://challenges.cloudflare.com/turnstile/v0/api.js" async defer>` from a
  static page, with no inline script; the token arrives in `cf-turnstile-response`.
- **Server check:** `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` (form or
  JSON), with:
  - `secret` (`TURNSTILE_SECRET_KEY`), `response` (the token, rejected if empty or longer than
    2048 characters) and `remoteip` (the trusted client IP);
  - `idempotency_key`: a UUIDv4 created per validation and reused only for retries of *that*
    request (up to 2 retries with back-off, 3 s timeout each).
- **Acceptance** needs all of:
  - `success == true`;
  - `hostname == TURNSTILE_EXPECTED_HOSTNAME` (`krunk.209.wf`);
  - `action` equal to the expected action for the endpoint;
  - `challenge_ts` no more than 300 s old.
- **Single use:**
  - Cloudflare rejects replays with `timeout-or-duplicate`.
  - The API also stores `SHA-256(token)` in `turnstile_seen` for 10 minutes and refuses
    duplicates before calling Cloudflare. A token therefore can't be used for two endpoints or
    two requests.
- **Errors:**
  - `error-codes` are logged (never the token).
  - The user sees a generic "Please complete the check again" (`turnstile_failed`).
  - If siteverify can't be reached, the API **fails closed** with `503`.
- **CSP:** only the pages that carry the widget (`/account/register`, `/account/login`,
  `/account/reset`, `/account/resend`, `/account/delete`) add
  `script-src https://challenges.cloudflare.com` and
  `frame-src https://challenges.cloudflare.com` to the existing CSP, per Caddy path. Every other
  page keeps the current `default-src 'none'; script-src 'self'; …`.
- **Keys:**
  - `TURNSTILE_SITE_KEY` is public: served to pages through `/api/v1/web/config`, so no inline
    script is needed.
  - `TURNSTILE_SECRET_KEY` lives in `.env` only.
  - Staging uses Cloudflare's test keys:
    - site keys `1x00000000000000000000AA` (pass) and `2x00000000000000000000AB` (fail);
    - secret keys `1x0000000000000000000000000000000AA` (pass),
      `2x0000000000000000000000000000000AA` (fail) and `3x0000000000000000000000000000000AA`
      (token already spent);
    - these accept only the dummy token `XXXX.DUMMY.TOKEN.XXXX`.

### 4.6 Website account pages (requirement 10)
- **Pages:** static files in `dist/server/site/account/`. Krunk's own UI talks to the API
  directly.
  - `register.html`, `login.html`, `verify.html`, `reset.html`, `resend.html`;
  - `index.html`: the overview, with email, 2FA, devices, sessions, export, sync reset and
    delete;
  - `link.html`: the device approval page, reached at `/link?code=` (rewritten to
    `/account/link.html`);
  - `delete.html`: account deletion, with Turnstile and re-auth.
- **JS:** a single `account.js`, served from the same origin. It uses `fetch` with
  `credentials: 'same-origin'` and the CSRF header.
- **CSP:** the existing CSP plus the Turnstile additions on five pages (§4.5). `connect-src`
  stays `'self'`.
- **Caching:** `Cache-Control: no-store` on `/account/*`.
- **Copy:** every page shows **"The Krunk website never asks for your sync passphrase or
  recovery key."**

### 4.7 Input validation, limits and logging (requirement 8)
- **Input:**
  - Request bodies are deserialized with serde using `deny_unknown_fields` and checked for type
    and length on every field (emails 254, labels 64, user agents 256).
  - `user_code` must match the Crockford set; ids are UUIDs; base64 fields are strict and
    length-checked.
  - Body limits use `tower-http`'s `RequestBodyLimitLayer`: 16 KiB by default, 2 MiB for
    `records/batch` and `rekey/batch`, and 512 KiB for `keys/commit`.
  - Request timeout: 30 s.
- **SQL:** sqlx with bound parameters only; no string-built SQL. Migrations are plain SQL files.
- **Logs:** structured `tracing` JSON lines. Each line records method, route template, status,
  latency, account and device ids, and the masked IP.
  - Logs **never** contain passwords, tokens, cookies, CSRF tokens, TOTP codes, Turnstile
    tokens, email bodies, envelopes, ciphertext, directories or `rr_wrap`s.
  - The log redaction has its own test: a request-replay corpus is grepped for secrets.
- **Headers:**
  - Every response carries the existing security headers: CSP, nosniff, `Referrer-Policy:
    no-referrer`, `X-Frame-Options: DENY`, Permissions-Policy, CORP and COOP, and HSTS.
  - `Cache-Control: no-store` for `/api` and `/account`.
  - No CORS: the API is same-origin for the website. Krunk is a native client and isn't
    subject to CORS.

### 4.8 Database (S1–S9 migrations)
All tables carry `account_id` with `ON DELETE CASCADE` from `accounts`, so deleting an account
deletes everything in one statement (§7).

**Accounts and authentication:**
- `accounts(id uuid pk, email citext unique, email_verified_at, pw_phc text, pepper_id smallint, pw_changed_at, totp_secret_enc bytea, totp_enabled bool, failed_logins int, locked_until, created_at, last_active_at)`

### 4.9 Migrations, backup and restore (requirement 10)
- **Migrations:**
  - `sqlx migrate` with embedded SQL files, applied by `api` at start inside a transaction
    holding `pg_advisory_lock(0x4b52554e4b)`, so only one instance migrates.
  - Migrations are forward-only and backward-compatible for one release (expand, then
    contract), so a rolled-back `api` still runs against the migrated schema.
  - A migration failure makes the `api` health check fail, and ai-pipe rolls the deploy back.
- **Backups:**
  - `dist/server/backup-db.sh` (added in S1) runs `docker compose exec -T db pg_dump -U krunk -Fc krunk`.
  - The dump is encrypted to the operator's `age` public key and written to the backup location
    (OPEN_QUESTIONS Q4), daily, keeping 14 days.
  - Backups contain only ciphertext, hashes and metadata, never keys. They still hold emails
    and IPs, hence the encryption and the retention limit.
- **Restore:**
  1. `docker compose stop api`.
  2. `pg_restore --clean --if-exists -d krunk` from a decrypted dump.
  3. Re-apply account deletions newer than the dump from the `deletions.log` export (a daily
     list of deleted account ids, kept with the backups).
  4. Start `api`.
  5. Smoke-test `GET /api/v1/web/config` and a test login.

  The restore drill is part of S1's acceptance and is repeated yearly.

## 5. Client (requirement 11)

### 5.1 Code layout
- **`sync-types/`** (new crate): serde types for envelopes, directories, API requests and
  responses, and the version constants. No crypto. The server and the client both depend on it,
  so the server never pulls in `core`.
- **`core/src/sync/`**: everything platform-independent, with no Windows APIs.
  - `crypto.rs`: HKDF labels, the seal, envelope AEAD, padding and the SAS.
  - `keys.rs`: directories, acceptance rules (PROTOCOL §4.4), rotation and escrow.
  - `engine.rs`: pull/push, merge orchestration, the queue and quota handling.
  - `collections/{history,bookmarks,passwords,settings,tabs,pins,lists}.rs`: per-collection
    adapters.
  - `normalize.rs`: URL normalization.
  - `state.rs`: the `sync.json` model.

  An `HttpClient` trait abstracts the network: `ffi::http` on Windows, OkHttp or Ktor on
  Android.
- **`app/src/browser/sync.rs`:** timers (unique ids) driving `spawn_job` work.
- **`app/src/ffi/http.rs`:** extended with `request(method, url, headers, body, max_bytes)` for
  POST/PUT/DELETE, JSON bodies, `Authorization`, and non-200 statuses (409, 410, 423, 429 with
  `Retry-After`).
- **`app/src/ffi/secure.rs`:** reuses `Dpapi` with a new entropy, `"Krunk sync state v1"`.
- **Android:** `core::sync` exported with UniFFI 0.32 as a Kotlin AAR (see `ANDROID_PLAN.md`
  §2).

### 5.2 Local storage and migrations (S5)
- **`browser.db` schema v5:**
  - `bookmarks` gains `guid BLOB UNIQUE NOT NULL` (16 random bytes, backfilled; the roots get
    fixed guids) and `modified INTEGER`;
  - new tables, the **single definition** (PROTOCOL §8 refers here):
    - `sync_items(collection, natural_key, record_id, server_seq, ver, bucket, dirty, deleted, origin_sync)`:
      `bucket` is the padding bucket of the last version (needed for tombstones, PROTOCOL §9.4);
      `origin_sync` marks items that arrived from sync (needed for unlinking with "delete synced
      data", §2);
    - `sync_queue(collection, natural_key, enqueued_at)`, for the AK collections only (the PAK
      collections queue inside the vault);
    - `sync_meta(key, value)`;
  - history keeps its existing tables; `sync_items` tracks which URLs have synced.
  - It is a forward-only migration in `Store::migrate`. Krunk ≤ 0.2 can't open a v5 database;
    release notes say so.
- **`vault.json` format 2:** an optional sealed field `sync` (PROTOCOL §8). Format-1 files load
  unchanged and are written as format 2 only once sync is set up.
- **`sync.json`:** new, created only at linking. It is DPAPI-wrapped (PROTOCOL §8) and deleted on
  unlink.
- **Where tokens live:** the refresh token in `sync.json` (DPAPI); the access token in memory;
  never in `browser.db`, logs or settings.

### 5.3 Engine and scheduling
- **Cadence (after linking):**
  - a sync 60 s after start;
  - then every 5 minutes;
  - and 30 s after a local change to a synced collection (debounced).
  - Each run is one `spawn_job`: refresh the access token if needed, `GET sync/state`, apply any
    directory changes, pull, merge and push.
- **Back-off:** exponential on network or 5xx errors (1 min up to 60 min). On `429` it follows
  `Retry-After`. On `423 rotation_pending` it keeps queueing and attempts the rotation if it is
  eligible (PROTOCOL §7).
- **Proxy:** the configured HTTP proxy, as the updater does. With a SOCKS proxy, sync is
  **paused** and the UI shows why: WinHTTP can't use SOCKS, and bypassing the proxy would leak
  the IP.
- **The vault and the PAK collections** (`passwords`, `never_save`): they sync only while the
  vault is unlocked. Their pending changes queue inside the vault's sealed `sync` field. Merges go through
  `Vault::upsert` and `Vault::delete`, so the vault keeps its own encryption and its atomic
  writes.
- **Private tabs** never record history and never sync anything.

### 5.4 UI
- **`krunk://settings` → Sync card:**
  - unlinked: *Link Krunk account*;
  - linked: email, status, last sync, per-collection toggles (history, bookmarks, passwords,
    settings, open tabs, pins and lists), *Manage* (opens `krunk://sync`) and *Sync now*.
- **`krunk://sync`** (a new `Page::Sync`, with its own `Sender::permits` allowlist):
  - **Link flow:** shows the user code and *Open the website*, then polls.
  - **Setup (first device):** shows the generated passphrase (*Choose my own* is optional) and
    the recovery key (Save/Print, retype its last 4-symbol data group). An explicit checkbox reads: "I
    understand: if I lose my passphrase, my recovery key and all my devices, my synced data
    cannot be recovered."
  - **Getting keys on a new device:** *Enter passphrase*, *Enter recovery key* or *Approve from
    another device* (shows the 6-digit entry field). The device lists are shown for confirmation.
  - **Devices:** decrypted names, platform and last sync. Actions: rename (a `device_meta`
    record), revoke, and "linked — no keys" warnings. Fork and tamper alarms appear here too.
  - **Sessions** (web and devices), with revoke.
  - **Change passphrase**, **New recovery key**, **Finish securing** (re-anchor) and
    **Unlink this device** (keep or delete local data).
- **Approval popup on a linked device:** "Approve *Device label*?" It shows the SAS and an
  optional *Also share passwords* (asks for the master password). It is a host-initiated popup
  of a new `PopupKind`, like the update prompt.
- **Safety copy** (the canonical string, used everywhere): "The Krunk website never asks for your
  sync passphrase or recovery key."

### 5.5 Settings allowlist (synced vs device-local)
- **Synced:** `searchEngine`, `customSearchUrl`, `startup`, `homepage`, `showHomeButton`,
  `showBookmarksBar`, `adblockEnabled`, `filterLists`, `blockThirdPartyCookies`, `httpsOnly`,
  `sendDnt`, `sendGpc`, `stripTrackingParams`, `clearOnExit`, `engineSecurityComponents`,
  `vaultAutolockMinutes`, `offerSavePasswords`, `askWhereToSave`, `defaultZoom`, `theme`.
- **Device-local (never synced):** `downloadDir`, `proxy`, `extraFlags`, `userAgent`,
  `hardwareAcceleration`, `tabSleepMinutes`, `tabDiscardEnabled`, `tabDiscardMinutes`,
  `checkUpdatesAutomatically`, `filterListsRev` (internal).
- A synced setting that needs a restart (`engineSecurityComponents`) applies at the next start,
  and the restart banner says so.

### 5.6 Errors and offline handling
- **Offline or 5xx:** status "Offline — will retry", and changes queue.
- **401 after a refresh:** status "Signed out — link again". The local data stays.
- **423:** status "Securing your account after a device was removed…". After 24 h without a
  rotation, the UI prompts for the passphrase.
- **410:** an automatic full reconcile (PROTOCOL §10.4).
- **Quota exceeded:** a clear message showing what is over its limit (the account's size or
  record count, or history). History evicts its oldest entries automatically, so the server's
  history cap is a backstop.
- **Fork or tamper alarm:** writes stop, a red banner appears in `krunk://sync` with *Details*
  and *Report*, and nothing is deleted.
- **Clock skew:** the HLC clamp (PROTOCOL §9.3). The status shows a warning if the local clock
  differs from the server's `Date` header by more than 5 minutes.

### 5.7 Android notes
- **Shared code:** the same `core::sync` via UniFFI.
- **Local key storage:** `sync.json` is wrapped by an Android Keystore AES-256-GCM key
  (StrongBox when available).
- **Vault:** the Android vault gets the same `sync` field model.
- **Scheduling:** WorkManager periodic work (15 minutes minimum) plus expedited work after
  changes.
- **Linking:** a Custom Tab opens `/link?code=`; deep-link return is optional.
- **Device approval:** the same SAS screens.
- **Argon2id at 128 MiB:** runs natively in Rust, outside the JVM heap. Low-end devices must be
  tested (S11 Android notes; OPEN_QUESTIONS).
- **GeckoView:** history and bookmarks come from the app's own stores, not from Gecko. The
  natural keys and URL normalization are byte-identical (PROTOCOL §9.6).

## 6. Data model summary (requirement 5)
- **Where it is specified:** collections, envelopes, versions, tombstones, conflict rules, pull
  and push, batches, horizon and full reconcile, first-sync merge and restore are in PROTOCOL
  §9–§10.
- **Proposed quotas** (OPEN_QUESTIONS Q5):
  - 50 MiB of ciphertext per account (server, `sync_state.bytes`);
  - 100,000 records (server, `sync_state.records`);
  - **20,000 history URLs.** The client evicts the oldest. The server counts history records
    separately (`sync_state.history_records`, since `c` is plaintext in the envelope) and refuses
    new history records beyond 25,000 with `quota_exceeded` and `collection: "history"`;
  - 64 KiB per record (server: envelope size);
  - 500 tabs per device record (client);
  - **10 active devices** (server, at link approval: `QUOTA_MAX_DEVICES`).
- **History retention:** the last 90 days are uploaded at first sync, and older history stays
  local. The server-side history is capped by count, not by age.
- **Tombstones:** clients purge tombstones older than 180 days (`purge: true` on a
  `records/batch` write). The server sets `purge_horizon_seq`, and older cursors get `410` and a
  full reconcile.

## 7. Account lifecycle (requirement 12)
- **Delete the account** (website, re-auth + Turnstile + TOTP if enabled):
  - **One transaction:** `DELETE FROM accounts WHERE id=$1` cascades to every table, including
    records, directories, escrow, devices, sessions and tokens. The account id is appended to
    `deletions.log`.
  - **Afterwards:**
    - every token and cookie returns 401 at once;
    - the receipt email is sent;
    - the page shows "deleted: 0 records, 0 devices remain";
    - an immediate `GET web/me` with the old cookie returns 401.
  - **Verifiable:** the export taken just before deletion lists the record count. Afterwards the
    API returns 401 for every token. An operator SQL check (`SELECT count(*) … WHERE account_id=…`
    → 0) is part of the S10 test.
  - **Backups:** the data stays in encrypted backups until they expire (14 days). A restore
    re-applies `deletions.log`, as stated in the privacy notice.
- **Export:**
  - `web/export`: account metadata, devices, sessions and the encrypted record envelopes. No
    directories, seals or escrow wraps: key material is served only to authenticated devices.
    Krunk's own `krunk://sync` export can include them.
  - `krunk://sync` → *Export decrypted data*: bookmarks HTML (`core::netscape`), history CSV
    and settings JSON. Passwords export only as an encrypted vault copy (needs the master
    password).
- **Sync reset (lost everything):** `web/sync/reset` deletes the keysets, escrow and records. The
  account and its linked devices stay, and the next device to set up creates a new key
  hierarchy.
- **Inactivity:** proposed off by default. If enabled (Q9), accounts with no login and no device
  sync for `INACTIVITY_DELETE_DAYS` (suggested 730) are warned by email at 30 and 7 days, then
  deleted as above.

## 8. Cloudflare and site integration details
- **Caddyfile additions (S1):**
  - `handle /api/* { reverse_proxy api:8081 { header_up X-Krunk-Client-IP {client_ip} } }`
    with `request_body max_size 2MiB`, matching the API's 2 MiB limit;
  - `CF-IPCountry` is forwarded **only** when the TCP peer is a trusted proxy (Cloudflare or the
    configured hop): `@untrusted not remote_ip <trusted ranges>` → `request_header @untrusted -CF-IPCountry`.
    A spoofed country can't reach the approval page;
  - `handle /account/*` serving the static pages;
  - a rewrite `/link` → `/account/link.html`;
  - `Cache-Control: no-store` on both;
  - per-path CSP for the Turnstile pages;
  - `trusted_proxies` and `client_ip_headers` (§4.4).
- **Existing behaviour:** `no-transform` (commit 8b4d004), the security headers and the update
  and download routes are unchanged.
